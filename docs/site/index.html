The NuclaDB CLI

A command line is how you actually get to know a database. NuclaDB ships two of them: a Go binary called nucladb-cli that talks straight to the gRPC server, and a Python one called nucladb that does the same thing for people who'd rather not build Go from source. This page walks through both, end to end: what they're for, how to install them, and every command they support.

If you haven't met NuclaDB yet: it's a vector search engine written from scratch, with HNSW indexing, a write-ahead log, mmap snapshots, tenant isolation, and (for the distributed build) Raft-replicated sharding. None of that is very useful if the only way to poke at it is writing a gRPC client by hand, which is the whole reason these CLIs exist. You should be able to bring up a server and start inserting and searching vectors in under a minute, without opening an editor.

Both CLIs talk to the exact same server over the exact same gRPC API. There's no functionality gap: pick whichever one fits your environment, and switch between them freely. Command names and flag meanings match; only the flag syntax differs (Go uses single dashes, Python uses double dashes, see below).

Install

Fastest path: pipes into go install, so it needs the Go toolchain but nothing else:

$ curl -fsSL https://raw.githubusercontent.com/Rakshit-gen/NuclaDB/main/install.sh | sh

No prebuilt-binary pipeline to maintain and no stale releases to go stale: it resolves straight to the latest commit on main the same way go install pkg@latest always does. Don't have Go? The script says so and points at go.dev/dl instead of failing silently.

Or build from source, or reach for the Python client instead:

Go binary: nucladb-cli
go build -o bin/nucladb-cli ./cmd/nucladb-cli
export PATH="$PWD/bin:$PATH"

No runtime dependency beyond the binary itself: it's a single static executable.

Python: nucladb
pip install ./clients/python

One command, no separate build step: pip reads the [project.scripts] entry point in pyproject.toml and drops nucladb on your PATH. Named nucladb rather than nucladb-cli deliberately, so it doesn't collide with the Go binary if you ever have both installed.

You'll also need a server to point either of them at:

go build -o bin/nucladbd ./cmd/nucladbd
./bin/nucladbd -data-dir=./data -dim=4 -metric=l2 &

Connecting

Both CLIs default to localhost:9090, and both read the same environment variable to override it: 

export NUCLADB_ADDR=localhost:9090

The Python CLI also accepts --addr on the command line if you'd rather not export anything, useful when you're scripting against several servers in the same shell.

Multi-tenancy

Every data command (insert, batch-upsert, search, delete) accepts a tenant id (-tenant in Go, --tenant in Python). A tenant isn't a label on shared data; it's a fully separate index: its own HNSW graph, its own WAL, its own snapshot file on disk. Two tenants can reuse the same vector id without ever colliding, and a search under one tenant will never surface another tenant's data.

Skip the flag and you land in the reserved default tenant, which carries no quota, so if you're just kicking the tires on one dataset, you never need to think about tenancy at all. Anything else has to be provisioned first with create-tenant.

Commands

Every example below was actually run against a live server, nothing here is guessed at. Go examples use nucladb-cli; Python examples use nucladb.

ping

Checks the server is reachable, over the standard gRPC health-check protocol (grpc.health.v1.Health/Check) rather than a made-up ad hoc endpoint, so anything else that speaks standard gRPC health checks (a load balancer, Kubernetes) understands it too. 

$ nucladb-cli ping
ok
$ nucladb ping
ok

create-tenant

Provisions a new, isolated tenant, with an optional storage quota and request-rate limit. Creating a tenant id that already exists is an error, not a silent no-op.

FlagRequiredDescription
idyesTenant id
max-vectorsnoStorage quota (default: unlimited)
max-qpsnoRequest-rate limit (default: unlimited)
$ nucladb-cli create-tenant -id=acme -max-vectors=1000000
created tenant "acme"
$ nucladb create-tenant --id acme --max-vectors 1000000
created tenant "acme"

insert

Insert or update (upsert) a single vector.

FlagRequiredDescription
idyesVector id: a decimal uint64, e.g. 1, 42
vectoryesComma-separated float32 values
metanokey=value pair; repeat for more
tenantnoTenant id (default: default)
Vector ids are decimal integers, not arbitrary strings: a request with id=v1 is rejected with INVALID_ARGUMENT. Worth knowing before you write a data-loading script around your own string ids. 
$ nucladb-cli insert -id=1 -vector=1,0,0,0 -meta=team=search
inserted id=1
$ nucladb insert --id 1 --vector 1,0,0,0 --meta team=search
inserted id=1

batch-upsert

Insert or update many vectors at once from a JSON file, the same shape both CLIs read:

[
  {"id": "10", "values": [1, 1, 0, 0]},
  {"id": "11", "values": [1, 1, 1, 0], "metadata": {"team": "infra"}}
]
FlagRequiredDescription
fileyesPath to the JSON array
tenantnoApplied to any item that doesn't set its own tenant
$ nucladb-cli batch-upsert -file=batch.json
upserted 2 vectors
$ nucladb batch-upsert --file batch.json
upserted 2 vectors

search

Find the nearest neighbors of a query vector. Lower score is closer, matching whatever distance metric the server was started with: a given nucladbd instance has one fixed metric, because HNSW bakes the metric into which neighbors get linked at insert time. You can't mix metrics per query.

FlagRequiredDescription
vectoryesComma-separated query vector
top-knoNumber of results (default: 10)
efnoCandidate beam width: higher means better recall, slower search (default: top-k)
filternokey=value metadata match; repeat for AND
tenantnoTenant id (default: default)
$ nucladb-cli search -vector=1,0,0,0 -top-k=3 -filter=team=infra
2	score=2.000000	map[team:infra]
$ nucladb search --vector 1,0,0,0 --top-k 3 --filter team=infra
2	score=2.000000	{'team': 'infra'}

The filter is a post-filter over an overfetched candidate set, not a pre-index scan: if a filter is very selective the search widens its internal candidate window and retries a bounded number of times rather than returning fewer than top-k silently.

delete

Delete a vector by id. This is worth calling out because it surprised us while building the Python SDK's own tests: deleting an id that doesn't exist (or that's already been deleted) is not an error. Deletes are idempotent by design, so WAL replay during crash recovery can safely re-apply the same delete without the engine treating it as a fault.

FlagRequiredDescription
idyesVector id to delete
tenantnoTenant id (default: default)
$ nucladb-cli delete -id=1
deleted=true
$ nucladb delete --id 1
deleted=true

$ nucladb delete --id 1
deleted=true    # still true, deleting twice is fine

Errors you'll hit

Two show up in normal use, both standard gRPC status codes rather than custom error shapes:

$ nucladb-cli insert -id=4 -tenant=acme -vector=1,1,1,1
nucladb-cli: rpc error: code = ResourceExhausted desc = engine: tenant storage quota exceeded

$ nucladb-cli insert -id=5 -tenant=doesnotexist -vector=1,1,1,1
nucladb-cli: rpc error: code = NotFound desc = engine: tenant not found

Exceeding max-qps returns the same ResourceExhausted code with a "rate limit exceeded" message instead.

REST equivalent

Everything above has a REST/JSON twin, served by nucladbd on its HTTP port (:8080 by default), handy if you'd rather curl it than install anything: 

POST   /v1/tenants        (CreateTenant)
POST   /v1/vectors        (Insert)
POST   /v1/vectors:batch  (BatchUpsert)
DELETE /v1/vectors/{id}   (Delete)
POST   /v1/search         (Search)
$ curl -s -X POST localhost:8080/v1/search -d '{"query":[1,0,0,0],"top_k":2}'
{"matches":[{"id":"3","score":2},{"id":"2","score":2,"metadata":{"team":"infra"}}]}

Using it as a library

The Python package is a real client, not just a CLI wrapper. Reach for it directly if you're scripting or writing tests rather than typing commands by hand: 

from nucladb import Client, DistanceMetric

with Client("localhost:9090") as db:
    db.insert("1", [1.0, 0.0, 0.0, 0.0], metadata={"team": "search"})
    for match in db.search([1.0, 0.0, 0.0, 0.0], top_k=3, metric=DistanceMetric.L2):
        print(match.id, match.score, match.metadata)

Full API and protobuf-regeneration notes live in clients/python/README.md.

Known limitations

Worth knowing rather than discovering the hard way: a tenant's quota (max-vectors / max-qps) lives in server process memory, set at create-tenant time. It isn't written to disk, so restarting nucladbd brings every tenant back with quota reset to unlimited. Vector and metadata data itself is fully durable across restarts (WAL + snapshot, same as anything else); only the quota policy resets. Re-applying quotas on startup is a documented follow-up, not a silent gap we're hoping no one notices.
